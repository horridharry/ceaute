# fleekd Reuse Audit

## Summary

fleekd is a Next.js 14 App Router application using React 18, JavaScript, Tailwind 3, Supabase Auth/Database/Storage, and early Stripe hooks. It has the same broad product shape as Ceaute: public provider pages, provider dashboard, treatments, weekly availability, booking selection, booking details, and appointment confirmation.

The useful work is mostly in mobile-first UI patterns and simple interaction flows. The implementation is not a strong direct-copy candidate because it depends on fleekd tables such as `businessprofiles`, `treatments`, `schedules`, and `bookings`, old route names under `/dashboard`, older Supabase helpers, public storage bucket assumptions, cookie-based booking state, and client-heavy data fetching.

Ceaute is already the source of truth for the route skeleton, schema, one shared account model, one provider page per owner, one active location, optional treatment groups, add-ons, booking snapshots, address privacy, and current Next/React/Supabase versions. Several Ceaute files are already cleaned-up descendants of fleekd screens, so the highest-value reuse is preserving selected UI and interaction details while rewriting data contracts against Ceaute.

## Discard List

- Old database schema and RLS in `001_initial_schema.sql` / `supabase/migrations/001_initial_schema.sql`; Ceaute's private `ceaute` schema and snapshot/ownership rules supersede it.
- Old auth identity assumptions that infer provider status from `businessprofiles`; Ceaute keeps one account with provider context.
- Cookie-based selected booking time and guest booking creation in `src/app/[username]/booking/actions.js`; Ceaute needs account-aware checkout holds and payment confirmation.
- Any direct use of `fleekd-app-bucket`; Ceaute storage paths and upload rules must be redesigned for portfolio/service images.
- `src/components/BusinessForm.jsx`, `AccountForm.jsx`, `ServicesForm.jsx`, `TreatmentsList.jsx`, and duplicated schedule copies; they appear older than the App Router dashboard screens.
- Prototype, mock data, old metadata, and public static gallery assets unless used only as visual inspiration.
- Old Stripe/webhook stubs; Ceaute payment rules and Stripe Connect model are materially different.

## Highest-Value User Actions To Migrate First

1. Provider creates/edits treatments, including image preview, validation, discovery category, optional group, add-ons, archive state, and pence/minute conversion.
2. Customer chooses a treatment/add-ons and then a valid time using the mobile treatment cards plus the three-day scheduler interaction.
3. Provider edits availability with weekday toggles, booking window, and whole blocked dates.

## Detailed Recommendation: First Migration

Start with provider treatment creation/editing because it unlocks public page content, booking duration, pricing, add-on eligibility, and later availability calculations. Preserve the fleekd form's mobile rhythm: image tile first, then name, description, price, duration controls, clear inline errors, back/save actions, and a separate destructive/archive action on edit.

Do not copy the fleekd implementation directly. Build it against Ceaute's provider data helpers and schema. Use `price_pence` and `duration_minutes`, require 15-minute duration increments, and include fields fleekd lacks: discovery category, optional treatment group selection/creation, display order, active/archive state, and add-on management. Replace client-side bucket upload with a Ceaute storage action that validates file type and size, writes provider-scoped paths, and stores only the resulting storage path/URL expected by Ceaute.

The safest approach is to reuse only small presentation pieces: the image preview interaction, form spacing, validation-message styling, and pending/disabled button states. Server actions should stay Ceaute-native, using `getSignedInProvider`, the `ceaute.treatment` table, and Ceaute's current route paths under `/provider/treatments`.
